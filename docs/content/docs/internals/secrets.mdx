`src/secrets/` owns credential storage. Two files compose the surface:

- **`<agentDir>/.env`** — `KEY=value` lines. Loaded by Docker via `--env-file`. User-owned. Gitignored.
- **`<agentDir>/secrets.json`** — `v2` envelope managed by `SecretsBackend` (`src/secrets/storage.ts`), a pi-ai `CredentialStore` used by `ModelRuntime`. Gitignored.
  - `providers.<id>` — `{ type: 'api_key', key: <Secret> }` or `{ type: 'oauth', access, refresh, expires, ... }` (pi-ai's `OAuthCredential`).
  - `channels.<adapter>` — per-adapter fields. `discord-bot`/`telegram-bot`/`webex-bot`: `{ token }`. `slack-bot`: `{ botToken, appToken }`. `kakaotalk`: `{ currentAccount, accounts: Record<id, KakaoAccountRecord> }` (multi-account, holds `email` + `encryptedPassword` for renewal — see [Host daemon](/docs/internals/hostd)).

Channel adapters never read the envelope directly. `hydrateChannelEnvFromSecrets` injects resolved values into `process.env[TOKEN_ENV]` at boot so `src/channels/manager.ts` keeps its env-based contract.

## The `Secret` shape

`Secret = string | { value?: string, env?: string }`. String form is shorthand for `{ value }`. Schema normalises both to object form. Precedence in `resolveSecret`:

1. `process.env[secret.env]` — explicit binding wins.
2. `process.env[defaultEnv]` — canonical fallback (from `CHANNEL_FIELD_ENV` / `KNOWN_PROVIDERS[id].apiKeyEnv` in `src/secrets/defaults.ts`).
3. `secret.value` — on-disk.
4. Missing.

## Env-wins, file-never-auto-mutated

- API-key providers: env var set at container boot → `modelRuntime.setRuntimeApiKey(...)` (in-memory only). `secrets.json` stays untouched.
- Channel fields: existing `process.env[TOKEN_ENV]` kept as-is. Only when env is unset does hydrate inject the resolved value.
- No auto-promotion. The `promoteChannelEnvIntoSecrets` module is gone.

## Credential-store idempotency

`CredentialStore.modify` holds `SecretsBackend`'s cross-process lock for its entire read-modify-write callback. **An unchanged API-key credential preserves its on-disk `Secret` bytes verbatim**; a changed non-empty key is rewrapped while retaining an authored `env`; an empty key is a no-op. OAuth credentials remain stateful flat token records. Provider writes merge only `providers.<id>`, so `channels.*` and all unrelated envelope slices remain untouched.

## Coding-agent authentication

`src/secrets/coding-agent-auth.ts` resolves `anthropic` and `openai-codex` credentials privately through one agent-scoped `ModelRuntime` and the same `SecretsBackend`/`CredentialStore.modify` lock used by normal agent requests. Persisted Anthropic OAuth wins over ambient API keys; Codex requires canonical subscription OAuth and never falls back to API-key billing. A rejected access-token generation is invalidated under that lock, followed by at most one coordinated refresh/retry before streaming; a concurrent refresh or host re-login is preserved.

Both CLI credential exporters and their serialization helpers are removed, along with Claude's custom credential alias. TypeClaw is the sole refresh owner for delegated runs. Claude receives only a fresh local capability, which the fixed-upstream broker replaces with `x-api-key` or an OAuth bearer plus subscription beta headers.

Codex uses a custom Responses provider in per-task `CODEX_HOME`, with `requires_openai_auth=false`, `env_key="TYPECLAW_CODING_AGENT_CAPABILITY"`, and a local `base_url`. There is no `auth.json`, ID-token synthesis, or refresh credential in the child. The broker sends only `POST https://chatgpt.com/backend-api/codex/responses`, injecting the OAuth bearer and `ChatGPT-Account-Id` from the matching trusted credential generation. Client account selectors are rejected, not forwarded. WebSockets and remote compaction are disabled; local compaction uses Responses.

Missing/revoked credentials fail only the requested task. The safe recovery is host-side `typeclaw provider add anthropic` or `typeclaw provider add openai-codex`, not reading a token, using a login tool, or passing credentials to the child. No provider credential appears in a tool receipt, argument, task file, or CLI environment. Live subscription qualification remains a release gate; fake transports cannot establish provider acceptance.

The confidentiality guarantee applies to private canonical credentials not also published in `.env`, prompts, source history, or other model-readable data. Ordinary operator-declared `.env` variables remain the existing expose-to-model-bash surface; delegation does not silently change that global policy.

## Envelope versioning

Writes are `v2`. Only the `v2` envelope is accepted on read. Legacy shapes (v1 envelope, pre-envelope flat shape, `auth.json`) are rejected with an error — migrate to `v2` manually before booting.

## TypeVault (experimental)

`typevault.enabled` (restart-required, default `false`) keeps the whole `secrets.json` envelope in the agent's own [TypeVault](https://github.com/typeclaw/typevault) vault, consumed from its `main` branch.

- **Layout.** `.typevault/` holds only ciphertext and signed manifests and is force-committed by the backup plugin (a system-managed root). `.typeclaw/typevault/` holds the agent's machine identity, the vault's sole owner, plus typevault's per-checkout state; it is gitignored. Both are in `RUNTIME_OWNED_SECRET_DIRS`, masked from every role. No human unlock and no host-owned key: copying the agent folder moves the vault.
- **Storage.** The envelope is one entry, `tv://typeclaw/secrets`, in the `runtime` tier. `secrets.json` becomes a marker (`"version": "typevault"`). `SecretsBackend` and `hydrateChannelEnvFromSecrets` follow the marker into the vault, so every call site is unchanged. A build without vault support refuses the marker as a non-v2 file instead of booting with no credentials. Sync reads and writes cross into `src/typevault/envelope-helper.ts` (the SDK is async); reads are cached until the vault's `entries/` directory changes.
- **Roles and grants.** The bundled `typevault` plugin (`src/bundled-plugins/typevault/`) gives every role a same-named tier. The built-in roles form an include tower, `owner` > `trusted` > `member` > `guest`, so a grant reaches its tier and every tier below it. The runtime tier is in none of them. A session whose role holds `vault.use` gets one live grant (12h, labelled `session:<id>:<n>`, revoked at `session.end`). Grant changes for a session run one at a time, and a role change or near-expiry revokes the old grant before its replacement is issued. A custom role named `runtime` never maps onto the runtime tier. Its bash receives `TYPEVAULT_GRANT` (passed through the inherited environment, never in the bwrap argv) and a `typevault` command on `PATH`. Through `reveal` binds rendered after the masks, the same bash gets read-only access to the ciphertext-only `.typevault/` and to the daemon's agent socket, mounted under the sandbox HOME. The admin sockets and the agent key stay masked. A grant can still `get --reveal`, so the tier is the boundary between roles; `tool.after` also scrubs from tool output every secret value the vault holds outside the runtime tier (read with the agent's own key, cached until entries change), so derived grants, still-running commands and expired grants are covered. If the vault cannot be read, the output is withheld rather than passed through. The plugin loads right after `security`, so this scrubbing runs before `tool-result-cap` truncates the output.
- **Asking a human.** `vault_request` opens a TypeVault `request` through the session's grant, using the daemon's agent socket. The daemon serves the one-time page on container port `typevault.promptPort` (default `8976`), binding it on the first request. `typeclaw doctor` warns (`channel.github.webhook-port`) if `channels.github.webhookPort` is set to the same port. A bind failure reaches the tool as `internal daemon error`, and the daemon keeps returning it until restart. The exception is in `.typeclaw/typevault/config/typevault/checkouts/*/run/daemon.log` on the host. The page becomes public through a `manual` tunnel to that port: the operator's own if `typeclaw.json` has one (by `upstreamPort` matching that port, or by the name `typevault` for a `cloudflare-named` tunnel, which has no port, so its Cloudflare origin must be retargeted by hand whenever `typevault.promptPort` changes), otherwise an implicit `cloudflare-quick` tunnel the runtime adds whenever TypeVault is enabled (`src/typevault/prompt-tunnel.ts`; the Dockerfile ships `cloudflared` for it). The tool rewrites the page link onto the tunnel's current URL (`src/tunnels/active.ts`), so a quick-tunnel URL that changes on restart still works. The browser encrypts the value to the tier before submitting it, so the tunnel carries only ciphertext. Any role may ask, and the value lands in the requester's tier.
- **Form filling.** `browser_fill_secret` also accepts a `tv://` reference. It reads through the same session grant (`src/bundled-plugins/typevault/runtime.ts`) and needs `vault.use` on top of `browser.shared`.
- **Lifecycle.** `reconcileTypevault` (`src/typevault/lifecycle.ts`) runs in `typeclaw start` while the container is down, before anything else touches `secrets.json`. Enabling copies the file into the vault, verifies it reads back byte-for-byte, then writes the marker. Disabling writes the vault copy back. Whichever side was live before the toggle wins. A dormant vault is resumed, never re-initialized, so entries stored through the vault survive disable and re-enable. A vault this agent's key cannot open is never replaced: start warns and keeps the current store.

## KakaoTalk renewal (encryption-at-rest)

KakaoTalk sub-device tokens have a ~7-day TTL; both access and refresh tokens expire on the same cycle. Once an account enters the renewal window, the host first uses the saved access token, refresh token, and `device_uuid` for a lightweight OAuth refresh grant. A rejected or missing refresh credential falls back to `attemptLogin(email, password, device_uuid)`; transport and server failures wait for the next daily tick instead of triggering the heavier login flow. The fallback password is stored as an AES-256-GCM envelope at `secrets.json#channels.kakaotalk.accounts.<id>.encryptedPassword`. AAD is `typeclaw:kakaotalk-password:v1:<containerName>:<accountId>`. The 32-byte key lives at `~/.typeclaw/keys/<containerName>.key` (0600 / dir 0700), **outside** the agent folder to defeat agent-folder-only leaks.

Threat model: defense against agent-folder-only leaks. Does NOT protect against full host compromise (OAuth tokens next to the blob already grant equivalent capability) or whole-home backups. Overriding `TYPECLAW_HOME` into the agent folder collapses the separation.

`getAccount()` strips `email`/`encryptedPassword`; renewal callers use `getAccountWithRenewalFields()`. `mergeUpstreamAccount` re-attaches the typeclaw-only fields on every write so SDK-driven refreshes don't strip them.

## Rules of thumb

- **Adding an adapter/provider with credentials** requires coordinated edits in `src/secrets/defaults.ts` + `schema.ts`: per-adapter field schema and `CHANNEL_FIELD_ENV` entry. Forgetting the env entry silently breaks injection at boot.
- **Never write env-resolved values to disk.** Use `modelRuntime.setRuntimeApiKey(...)` (in-memory) rather than `CredentialStore.modify(...)`.
- **`CredentialStore.modify` is the only runtime (model-driven/pi) provider mutation path and runs under the file lock.** Host-stage initialization and `provider add`/`provider remove` use synchronous locked API-key writers. Every path changes one `providers.<id>` entry while preserving sibling providers, `channels.*`, and unknown envelope slices.
- **`.env` and `secrets.json` are peers, not migration source/sink.** `typeclaw doctor` surfaces resolution origin; no boot-time auto-migration.
