The walkthrough is at [Add a plugin](/docs/guides/write-a-plugin). The shape is at [/concepts/plugins-and-stages](/docs/concepts/plugins-and-stages). This page is the contract. The source of truth is `src/plugin/types.ts` and `src/plugin/define.ts`.

## TypeScript consumers

Import values and types from `typeclaw/plugin`. Published packages include a declaration graph under `dist/types/`; the `types` export selects it for TypeScript, while Bun continues to load the existing TypeScript runtime entrypoint.

Consumers do not need a `paths` mapping for TypeClaw's internal `@/*` alias. The declarations use relative imports, including explicit extensions for NodeNext resolution. With `skipLibCheck`, TypeScript can skip checking dependency declarations instead of repeatedly checking TypeClaw's implementation sources. Keep your own plugin code under normal strict checking.

For a linked development checkout, run `bun run build:types` after SDK changes before typechecking a consumer. Packing or publishing runs that build automatically through `prepack`.

## `definePlugin`

```ts
import { definePlugin } from 'typeclaw/plugin'

export default definePlugin({
  configSchema, // optional: z.ZodType<TConfig>
  permissions, // optional: readonly string[]
  ownerWildcardExclusions, // optional: readonly string[]
  commands, // optional: Record<string, PluginCommand>
  plugin: async (ctx) => {
    return {} // PluginExports
  },
})
```

The plugin's **name is not declared here** — the loader derives it from the entry. For a local/path plugin (`./packages/foo`) the name is the resolved path's basename (minus a `.ts`/`.js`/… extension); for an npm plugin it's `package.json#name` run through `derivePluginNameFromPackage` (drops a `@scope/` and a `typeclaw-plugin-` prefix). That derived name scopes the config block (`typeclaw.json#<name>`) and namespaces permissions.

| Field                     | Required | Notes                                                                                                                            |
| ------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `configSchema`            | no       | Zod schema for the plugin's config block; parsed result is handed to `plugin` as `ctx.config`. Omit for `unknown`.               |
| `permissions`             | no       | every permission this plugin both declares and consumes; read before `plugin` runs                                               |
| `ownerWildcardExclusions` | no       | permission strings the owner wildcard sentinel MUST NOT auto-expand to (used by `security` to keep high-tier bypasses off owner) |
| `commands`                | no       | declared by-value so the host-stage CLI can dispatch them without booting plugin runtime state                                   |
| `plugin`                  | yes      | **async** factory; receives the live `PluginContext`, returns the plugin's `PluginExports`                                       |

## `PluginContext`

```ts
type PluginContext<TConfig = never> = {
  readonly name: string // derived plugin name
  readonly version: string | undefined
  readonly agentDir: string // absolute; '/agent' in container
  readonly config: TConfig // parsed per configSchema (the ctx is frozen; the config object itself is not)
  readonly logger: PluginLogger // .info / .warn / .error
  readonly permissions: PermissionService // .has(origin, perm) etc.
  readonly github: PluginGithubServices // .resolveTokenForRepo
  spawnSubagent: (name: string, payload?: unknown, options?: SpawnSubagentOptions) => Promise<void>
}

type SpawnSubagentOptions = {
  parentSessionId?: string
  spawnedByOrigin?: SessionOrigin
}
```

`spawnSubagent` resolves `spawnedByRole` from `spawnedByOrigin` via the `PermissionService`, so the spawning session's role is inherited rather than forged. Hook handlers that own an origin (e.g. `session.idle`, `session.turn.end`) should pass `parentSessionId` and `spawnedByOrigin: event.origin`.

## `PluginExports`

Returned from the `plugin(ctx)` factory. All fields optional.

```ts
type PluginExports = {
  tools?: Record<string, Tool<any>>
  subagents?: Record<string, Subagent<any>>
  cronJobs?: Record<string, PluginCronJob>
  skills?: Record<string, PluginSkill>
  skillsDirs?: string[]
  hooks?: Hooks
  doctorChecks?: Record<string, PluginDoctorCheck>
}
```

Commands are declared on `definePlugin` (by-value), not returned here.

### Tool

```ts
type Tool<P = unknown> = {
  description: string
  parameters: z.ZodType<P>
  fileOperands?: {
    input?: readonly string[]
    output?: readonly string[]
    create?: readonly string[]
    destructive?: readonly string[]
    nonFile?: readonly string[]
  }
  execute: (args: P, ctx: ToolContext) => Promise<ToolResult>
}

type ToolContext = {
  signal: AbortSignal | undefined // fires when the agent cancels the call
  sessionId: string
  agentDir: string
  logger: ToolLogger
}

type ToolResult = {
  content: ContentPart[] // { type: 'text'; text } | { type: 'image'; mimeType; data }
  details?: unknown
}
```

`fileOperands` declares which string fields carry local filesystem paths. Entries are dotted operand paths: for example, `source.path` addresses `args.source.path`, while `attachments.path` addresses the `path` field of each object in an `attachments` array (array indexes are not part of the path). `input` operands pass through normal authorization and execute against bounded immutable snapshots. `output` operands are authorized and descriptor-anchored by the runtime before dispatch; a missing target is atomically reserved as a new single-link regular file, and the plugin writes the rewritten path it receives without performing its own anchoring. `create` is the exclusive-creation variant: the runtime verifies the destination is absent and descriptor-anchors its parent, while the plugin must create the rewritten path with `O_CREAT | O_EXCL`; cleanup verifies the resulting file is single-link and remains below the authorized parent. `destructive` operands are not treated as reads or snapshotted, so the tool's delete/move primitive remains responsible for their authorization and anchoring. `nonFile` marks a field as a remote identifier or control token even if its value happens to name an existing agent-root entry; use it narrowly and never for a field the tool may open locally. MCP servers declare the same five categories over the wire via `_meta['x-file-operands']`; see [MCP](/docs/reference/mcp) for the wire format and malformed-declaration rules.

Input, output, and create declarations may coexist. The runtime snapshots inputs and anchors destinations before dispatch, restores rewritten paths in inverse order in the result, and cleans their resources in reverse order. A failure while anchoring destinations also removes any input snapshots already acquired.

Undeclared filesystem-capable strings fail closed even when the referenced entry does not exist yet. File-shaped keys, explicit relative or absolute paths, canonical credential names, and values resolving to existing entries are rejected before dispatch; existing-entry detection runs before every semantic exemption and also emits a developer warning naming the operand path. The only spelling-based exemptions are narrow grammars for clear remote/control values: non-`file:` URLs, strict repository slugs under repository-shaped keys, numeric dates/fractions under their matching keys, safe `/vN/...` API routes under `path`, and package coordinates under package-shaped keys. Traversal, malformed variants, and broader keys still fail closed. A `file:` URI explicitly opts an undeclared value into input authorization and immutable snapshotting. Exact first-party exemptions, whole-tool no-local-file declarations, and plugin `fileOperands.nonFile` declarations remain authoritative. Declare every local path a tool accepts; declared inputs stay pinned.

`defineTool(tool)` is an identity helper for type inference. Built-in tools are referenced by tagged ref (`readTool`, `bashTool`, `editTool`, `writeTool`, `grepTool`, `findTool`, `lsTool`, `webSearchTool`, `webFetchTool`) — useful when wiring a subagent's `tools` list.

### Optional `eval` tool

`eval` is registered by the runtime when `eval.enabled` and the session's origin permit it, and only if the session already has unrestricted bash. It is not a new `BuiltinToolRef` and does not need to be added to a subagent's declared tools. A subagent's `bashPolicy` still excludes it.

The input is `{ code: string, timeoutMs?: number }`. Inside JavaScript cells, `tool.<activeName>(args)` invokes the same wrapped definition as a direct call, including plugin validation and hooks. `parallel(thunks)` batches independent calls; `print` and `display` return selected text. Recursion, orchestration, posting, lifecycle/role mutation, and MCP dispatch are refused. See [Eval kernel](/docs/internals/eval) for the exact refusal list and limits.

### Subagent

```ts
type Subagent<P = unknown> = SubagentShared<P> & {
  tools?: BuiltinToolRef[] // built-in tools, by tagged ref
  customTools?: Tool<any>[] // plugin-contributed tools
}
```

A subagent inherits its system prompt, payload schema, and optional `inFlightKey(payload)` from `SubagentShared`. Stream and direct plugin dispatch default to the subagent name; tool spawns without an explicit key remain request-unique. A declared key deduplicates matching work within a trusted parent-session scope when one exists, and process-wide for scheduler dispatches without a parent. Memory's `memory-logger` keys by `parentSessionId` so different parent sessions run in parallel while duplicate runs against the same session deduplicate. `defineSubagent(subagent)` is the identity helper.

An optional subagent `handler(ctx, runSession)` can call `runSession({ userPrompt, onFinalMessage })`. The callback fires after a completed session turn with the terminal assistant message's text (trimmed), or `null` when the terminal message is empty or the provider failed. It receives raw assistant text, not the `<review>`/`<report>` block projection used by subagent orchestration. The handler may persist the returned text with trusted plugin code rather than granting the model a file-write tool. `runSession` itself still resolves to `void`; `ctx.spawnSubagent` does not return the text.

### Cron

`cronJobs` is a `Record<string, PluginCronJob>`; the runtime prefixes each key with `__plugin_<plugin-name>_` to form the global cron id (no collision with `cron.json` user jobs or across plugins). `PluginCronJob` is a discriminated union on `kind`:

```ts
type PluginPromptCronJob = {
  schedule: string
  kind: 'prompt'
  prompt: string
  enabled?: boolean
  timezone?: string
  subagent?: string // invoke a subagent instead of prompting
  payload?: unknown
}

type PluginExecCronJob = {
  schedule: string
  kind: 'exec'
  command: string[]
  enabled?: boolean
  timezone?: string
}

type PluginHandlerCronJob = {
  schedule: string
  kind: 'handler'
  handler: (ctx: CronHandlerContext) => Promise<void>
  enabled?: boolean
  timezone?: string
}
```

`kind: 'handler'` is plugin-only — a TypeScript function reference, so it cannot appear in `cron.json` (the schema gate limits user files to `prompt` and `exec`). Use it when a job needs imperative control flow (probe → maybe prompt → write file) in the same plugin as the logic. `CronHandlerContext` mirrors a command's LLM-call surface (`prompt`, `subagent`, `exec`) plus `jobId`, `name`, `agentDir`, `logger`, `signal`, `permissions`, and a cron-shaped `origin` that stamps provenance on anything the handler spawns.

### Hooks

```ts
type Hooks = {
  'session.start'?: (event: SessionStartEvent, ctx: HookContext) => void | Promise<void>
  'session.end'?: (event: SessionEndEvent, ctx: HookContext) => void | Promise<void>
  'session.idle'?: (event: SessionIdleEvent, ctx: HookContext) => void | Promise<void>
  'session.prompt'?: (event: SessionPromptEvent, ctx: HookContext) => void | Promise<void>
  'session.turn.start'?: (event: SessionTurnStartEvent, ctx: HookContext) => void | Promise<void>
  'session.turn.end'?: (event: SessionTurnEndEvent, ctx: HookContext) => void | Promise<void>
  'tool.before'?: (event: ToolBeforeEvent, ctx: HookContext) => ToolBeforeResult | Promise<ToolBeforeResult>
  'tool.after'?: (event: ToolAfterEvent, ctx: HookContext) => void | Promise<void>
  'channel.message.observed'?: (event: ChannelMessageObservedEvent, ctx: HookContext) => void | Promise<void>
  'channel.outbound.before'?: (
    event: ChannelOutboundBeforeEvent,
    ctx: HookContext,
  ) => ChannelOutboundBeforeResult | Promise<ChannelOutboundBeforeResult>
}

type HookContext = { agentDir: string; pluginName: string; logger: PluginLogger }
```

At registration, unknown hook names produce a warning identifying the plugin and the unrecognized key. They are ignored; supported handlers from the same plugin remain active. This runtime check also covers JavaScript plugins and extra keys returned by async factories, which TypeScript's excess-property checks can miss. For an explicit compile-time check, write the hook object as `{ ... } satisfies Hooks`.

`tool.before` is the gate. Return:

```ts
type ToolBeforeResult = void | undefined | { block: true; reason: string }
```

Return nothing (or `undefined`) to allow; return `{ block: true, reason }` to block. The bundled `security` plugin returns the block variant for its tier-based policies. It fires for plugin-defined tools and TypeClaw-exposed built-in tools (read/bash/edit/write/grep/find/ls).

`tool.after` is read-only; use it for logging, metrics, and side-channel cleanup.

`session.prompt` brackets system-prompt assembly — mutate near the **end** of `event.prompt` to preserve provider prompt-cache hits; mutations near the start invalidate the cache on every call. `session.turn.start` / `session.turn.end` bracket every `session.prompt(...)` turn (distinct from `session.start` / `session.end`, which bracket session lifetime). `session.idle` carries an `idleMs` window; plugins wanting delayed reactions install their own `setTimeout`.

#### Channel edge hooks

These are optional interfaces for trusted, in-process plugins. They keep application-specific collection and copy-editing policy outside the runtime. Existing `tool.before` is not equivalent: it neither sees discarded inbound events nor covers text generated outside a tool call.

**Synthetic use cases.** The following examples are invented, not redacted production conversations:

- In `#operations-example`, a person asks another person to change `EXAMPLE-042` from 12 units to 10, then edits and deletes the message. The bot is never mentioned. A private collection plugin needs the received original/edit/delete envelopes without opening a model session. A history poll cannot reconstruct every removed revision or preserve receipt order.
- A copy-editing plugin changes “The report will been ready at 15:00” to “The report will be ready at 15:00”. The same organization wants its existing runtime notices and `!help`/`/help` responses reviewed, not only `channel_reply`. The plugin owns factual/identifier preservation; the runtime owns routing, authorization and delivery accounting.

**`channel.message.observed` — observe, do not admit or wake.**

```ts
type ChannelMessageObservedEvent = {
  readonly adapter: 'slack-bot'
  readonly workspace: string | null
  readonly selfUserId: string | null
  readonly receivedAt: number
  readonly event: SlackObservedMessage
}
```

- Slack-bot Socket Mode `message` deliveries only, after transport ack and before edit filtering, classification, command handling and deduplication. Normal messages, non-mentions, edits, deletes, self/bot messages and duplicate deliveries are included. `app_mention`-only deliveries are not included.
- `event` preserves the received fields, including nested `message`/`previous_message`, `deleted_ts` and opaque timestamp strings. It is a deep-frozen snapshot shared by the observers for that receipt. Workspace/self identity can be null before authentication.
- Handlers are scheduled without awaiting them on the routing path. Each has a 10-second asynchronous ceiling. A throw, rejection, timeout or snapshot failure cannot change admission or prevent ordinary routing; runtime diagnostics contain the plugin and failure category, not the payload or thrown value.
- No subscribers means no snapshot or observer work. Reloads affect subsequent receipts; a handler already scheduled belongs to the registration set at receipt.
- This is best-effort observation, not a durable journal, replay API, permission grant or exactly-once stream. Slack scopes/membership still bound what arrives. Plugins own deduplication, retention, persistence and access controls, including deletion policy. Asynchronous completion order is not receipt order.

**`channel.outbound.before` — transform text, do not authorize or gate delivery.**

```ts
type ChannelOutboundBeforeEvent = {
  readonly adapter: string
  readonly workspace: string
  readonly chat: string
  readonly thread?: string
  readonly text: string
  readonly op: 'send' | 'edit'
  readonly messageId?: string
  readonly source: 'tool' | 'system'
  readonly outputKind?: 'substantive' | 'status' | 'meta'
  readonly origin?: { readonly kind: SessionOrigin['kind']; readonly jobId?: string }
}
type ChannelOutboundBeforeResult = { text: string } | undefined
```

- Runs once per logical operation, immediately before handing application text to the adapter. Adapter markdown rendering, chunking and platform delivery happen afterward. Hooks compose in registration order; each receives frozen input containing the previous valid replacement.
- Only an own `{ text: nonEmptyString }` result replaces text. `undefined`, malformed/empty results, exceptions and a 30-second per-handler timeout retain the preceding text and continue. Late results cannot replace a delivery. These ceilings do not preempt synchronous plugin code or cancel a plugin's external work.
- Covers router sends/replies, attachment captions, edits, and existing router-generated system output, including recovery transport calls. Slack-bot thread-control replies use the same transform without entering tool-send accounting. Native slash responses acknowledge immediately, then publish one reviewed **ephemeral** response via the validated Slack `response_url`; no reviewer preserves the existing ack-with-text behavior. If that URL is absent/unsafe, the response fails open to the original ack without contacting another host.
- Slack-bot control responses additionally have a one-second **total** review budget, retaining the original response when it expires. This leaves room under the runtime's eight-second shutdown deadline after an authorized restart has already begun. Slow asynchronous reviewers may finish later, but cannot send a second response.
- Attachment-only sends expose `text: ''` but cannot gain a caption. Reactions, typing indicators, rich-block internals, other adapters' native control responses and network writes made directly by external tools/plugins are outside this contract. No previously suppressed runtime notice is enabled by installing a hook.
- Hooks cannot return destinations, permissions, attachments, blocking/drop flags or turn-completion flags. Runtime-owned `source`, `outputKind` and optional session-kind/job provenance are not model arguments and grant no authority. Tool provenance is resolved at execution time, not cached from an earlier session origin.
- Existing admission, duplicate reservations, send caps, sticky engagement and work-completion decisions remain based on the authored operation. Review cannot make a duplicate eligible by rewriting it nondeterministically. Replacements pass the existing reasoning/flood protections; an invalid replacement retains the original text.
- Successful reviewed router sends/edits return `deliveredText`, the post-hook application text handed to the adapter, so channel-tool receipts echo that text rather than the draft. It is not a platform-byte receipt; message IDs and platform errors keep their existing meaning.

These hooks are **not** a sandbox or fail-closed DLP boundary. Plugins already run with runtime trust, and raw events may include private-channel/DM content. Do not feed raw observations into model prompts, logs or third-party services without the operator's own policy. The runtime does not start a model, persist a transcript, or add a network destination merely because a hook is registered.

### Doctor checks

```ts
type PluginDoctorCheck = {
  description: string
  category?: string
  run: (ctx: PluginDoctorContext) => Promise<PluginCheckResult>
}
```

Each check is read-only by default. Declaring `fix.apply` on the returned `PluginCheckResult` opts it into `typeclaw doctor --fix`, where the host serializes plugin fixes, validates each `changedPaths` entry stays inside the agent folder, and commits the union of all fixes in a single commit.

## Commands

Commands are declared by-value on `definePlugin#commands` so the host-stage CLI can dispatch them without booting plugin runtime state. `surface` controls where a command may run:

```ts
type PluginCommand = ContainerCommand | HostCommand | EitherCommand
```

| `surface`     | Runs                        | Context surface                                       |
| ------------- | --------------------------- | ----------------------------------------------------- |
| `'container'` | inside the agent runtime    | `prompt`, `subagent`, `exec`, `origin`, `permissions` |
| `'host'`      | on the user's machine       | streams + `agentDir` (host path), `logger`, `signal`  |
| `'either'`    | whichever stage was invoked | intersection of the two                               |

`defineCommand(cmd)` infers the context type from `surface` and types `args` from a `z.ZodObject` (v1 constraint: primitive leaves so `--help` can render `--<name>=<type>`). Container commands may set `isolated: true` to spawn a fresh Bun subprocess (~150ms cold-start) for isolation from the agent.

## Lifecycle

Plugins load once at container start. They can:

- Expose tools, subagents, cron jobs, skills, hooks, doctor checks, and commands
- Read live config via `ctx.config` (boot-only fields are snapshots; reloadable fields are live)
- Spawn subagents with provenance (`spawnedByRole` is resolved from the parent origin)

Plugins cannot:

- Change which other plugins are loaded
- Rewrite the Dockerfile or escape the container
- Issue tool calls themselves (they expose tools; the agent decides when to call them)
