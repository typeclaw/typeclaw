Part of the [channel adapters](/docs/reference/channel-adapters) family.

Transport: **webhook delivery** (public URL required). Setup walkthrough: [Add a channel](/docs/guides/add-a-channel).

## Crash recovery correlation

Interruption notices carry a stable opaque HTML comment marker. Recovery
paginates the exact issue/PR comments, PR review replies, or discussion comments.
It requires the authenticated actor (numeric ID for REST, authenticated login for
GraphQL discussion authors) and matching marker; review replies must also match
their original parent comment. A failed page read never proves absence.
Account changes block delivery rather than redirect it. Deleted comments or
markers can cause duplicate notices after an ambiguous send; delivery is
at-least-once, not exactly-once. Other adapters without provable correlation
also retry ambiguous sends and may produce duplicates.

<Callout type="warn" title="Public URL required">
The `github` adapter needs a public URL to receive webhook events. Set `channels.github.webhookUrl` in `typeclaw.json`, or configure a tunnel entry with `for: { kind: 'channel', name: 'github' }`. Without one, webhook registration is skipped and no events arrive. See [Add a tunnel](/docs/guides/first-tunnel).
</Callout>

## Own-reaction cleanup

Waiting cleanup reads every reaction page before deleting anything, matches the exact emoji and authenticated numeric actor, and deletes only that actor's matching reaction IDs. Both PAT and App authentication resolve the actor through `getSelf`; login aliases are not ownership evidence. A later-page error does not prove absence, and account rotation blocks the original cleanup. Replies do not await cleanup transport. Protected review acknowledgments that share the engagement emoji survive temporary cleanup and reboot.

## Auth

Two modes. Both require `channels.github.webhookSecret` in [`secrets.json`](/docs/reference/secrets-json).

### PAT mode

```json
{
  "channels": {
    "github": {
      "auth": { "type": "pat", "token": "github_pat_…" },
      "webhookSecret": "…"
    }
  }
}
```

Fine-grained PAT. The bot acts as a real GitHub user. Model-driven commands do **not** receive the process environment wholesale: TypeClaw brokers the PAT into one standalone, statically inspected `gh` invocation only when the session role has `fs.see.secrets` or `security.bypass.medium`. Lower-trust roles do not receive a long-lived PAT; configure App mode for their repository operations.

PAT brokerage deliberately excludes shapes where the destination cannot be enforced:

- `gh api graphql` is blocked for PATs because the query can name repositories that are not visible in argv. Use a repository-confined REST endpoint, App mode with an explicit `-R owner/repo` mint hint, or run the PAT-backed query host-side.
- A PAT explicitly declared in the agent `.env` can be brokered to one standalone GitHub `git push` for a role entitled to use secrets. TypeClaw verifies that the live value is exactly the operator-declared value, suppresses ambient aliases, disables hooks and credential helpers, forces exact-repository TLS verification with the system CA bundle, clears local HTTP/remote proxy settings, and delivers the PAT through `GIT_ASKPASS` rather than argv or Git config. Reads (`clone`, `fetch`, `pull`, `ls-remote`) remain unbrokered on the PAT path: public repositories work anonymously and private ones fail at Git's own auth. A process-only, replaced, malformed, or unauthorized PAT never silently falls through to another broad credential. `gh pr checkout` remains unavailable; broad private-repository reviews use the reviewer-only `github_prepare_review_checkout` action.
- Chained commands, substitutions, aliases, extensions, auth/config management, token-display forms (`gh auth token`, `gh auth status -t`, and `--show-token`), and other shapes that could expose the command-scoped token are rejected rather than run with broad ambient credentials.
- Flag names are interpreted per command, not globally. `-F` is `--field` for `gh api` and `gh workflow run` but `--body-file` on `pr`/`issue` commands, so it is accepted only where it means a field; file-backed input is unavailable under every spelling.

### GitHub App mode

```json
{
  "channels": {
    "github": {
      "auth": { "type": "app", "appId": 123456, "privateKey": "-----BEGIN RSA PRIVATE KEY-----\n…" },
      "webhookSecret": "…"
    }
  }
}
```

Installations are resolved per repository, and validated model-driven `gh` commands receive a short-lived installation token minted for that exact `owner/repo`. App credentials are never seeded into the ambient process `GH_TOKEN`; validated `gh` calls and runtime-owned consumers mint through the repository-scoped token bridge instead. An operator-authored `GH_TOKEN` remains untouched.

App-backed GraphQL requires an explicit repository mint hint (`gh api graphql -R owner/repo ...`); TypeClaw consumes `-R`, mints that repository's installation token, and removes the unsupported flag before invoking `gh api`. Review-producing mutations are rejected from the shell-normalized query before minting so they cannot bypass the formal-review coordinator.

Authenticated network Git (`clone`, `fetch`, `pull`, `push`, `ls-remote`) runs in model-driven bash under App mode as a **single bare `git`** (or the `cd <path> && git …` rewrite): command analysis resolves the `owner/repo`, mints its installation token, and delivers it only through `GIT_ASKPASS` env, never the command string. The command-scoped Git config also forces exact-repository TLS verification with the system CA bundle and clears HTTP/remote proxy settings so repository-local config cannot intercept the credential. Because that token would be inherited by any sibling process in a compound command, chained forms are rejected — with one exception for the common "clone then look" workflow: `git clone <url> <dir> && <tail>` is allowed when `<tail>` is not itself a `git` command. The clone runs with the token, then the tail is `exec`'d into a fresh shell under `/usr/bin/env -u …` that unsets every injected credential, so the inspection commands (`cd`, `grep`, `cat`, `ls`, …) never see the token. Reading canonical secret files and dumping the environment stay blocked by the independent sandbox mask and secret-exfil guards, not this broker.

### Trusted-runtime GitHub CLI store

Credential precedence for `git push` is GitHub App, then an authoritative PAT declared in the agent `.env`, then the GitHub channel's own PAT when `channels.github` uses PAT auth. The channel PAT funds a push only for a destination listed in `channels.github.repos[]` and only for roles entitled to use a PAT (`fs.see.secrets` or `security.bypass.medium`, such as `owner`); sandboxed roles never receive it. The trusted GitHub CLI store is **never** a push credential, even with `importHostAuth` enabled: the host `gh` login is the operator’s identity, so a push it signed would land on GitHub as the operator. The store funds brokered `gh` work only, and `fetch`/`clone` never use it.

The store is **opt-in per agent**, because the host `gh` login is the operator's identity, not the agent's. Without opt-in, `typeclaw start` never copies it and removes any `githubCli` entry an earlier start left in `secrets.json`. To opt in:

```json
{
  "githubCli": { "importHostAuth": true }
}
```

On the host, select the account with `gh auth login --hostname github.com`. With opt-in enabled, the next real `typeclaw start` or `typeclaw restart` automatically captures that account while ignoring ambient GitHub token variables, asks `gh auth login --with-token` to generate an isolated `hosts.yml`, and persists only that generated artifact in masked `secrets.json`. A `typeclaw start` that finds the container already running is a no-op and does not refresh credentials. On container boot TypeClaw reconstructs `/home/agent/.config/gh/hosts.yml`; the store remains hidden from model bash and non-bash tools and the operator's full GitHub CLI configuration is never copied. If refresh fails, TypeClaw keeps the previously persisted store and prints recovery guidance.

A GitHub App can't be a `requested_reviewer` — use its [decoy user account](/docs/internals/github-decoy-reviewer) instead.

CLI: `typeclaw channel add github` (interactive; offers to create a Cloudflare tunnel), `typeclaw channel set github` (rotate credentials).

## Adapter-specific config fields

These extend the [shared base config](/docs/reference/channel-adapters) for `channels.github`:

| Field            | Type                                      | Default              | Notes                                                                                                            |
| ---------------- | ----------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `webhookUrl`     | string                                    | —                    | Public URL for webhook delivery; tunnel used when omitted                                                        |
| `webhookPort`    | number                                    | `8975`               | Container-side port the webhook server listens on                                                                |
| `eventAllowlist` | string[]                                  | (12 defaults)        | Events that trigger the adapter                                                                                  |
| `repos`          | string[]                                  | `[]`                 | `owner/name` pairs; hooks auto-registered on start; members may push branches to them (see below)                |
| `review.on`      | `'review_requested' \| 'opened' \| 'off'` | `'review_requested'` | When to fire a review                                                                                            |
| `review.approve` | boolean                                   | `true`               | `false` downgrades APPROVE verdicts to COMMENT; a re-review that clears the bot's own block dismisses it instead |
| `review.check`   | boolean                                   | `true`               | Show the bot's review as a check named after the bot on the reviewed commit; `false` opts out (see below)        |

Default `eventAllowlist`:

```
issue_comment.created
pull_request_review_comment.created
discussion_comment.created
issues.opened
pull_request.opened
pull_request.converted_to_draft
pull_request.ready_for_review
pull_request.review_requested
pull_request.review_request_removed
pull_request.synchronize
discussion.created
pull_request_review.submitted
```

## Review behavior

Reviews fire on the event named in `review.on` (default `review_requested`).

- **PAT mode**: the bot is requested by its GitHub login.
- **App mode**: request the [decoy user account](/docs/internals/github-decoy-reviewer); the App itself can't be a reviewer.
- Team-reviewer requests are honored when the bot is a member of the requested team.

### Draft transitions

Converting a PR to draft immediately stops its in-progress review turn, cancels its reviewer subagent, and clears pending review rounds. A later `ready_for_review` starts a fresh review.

Custom `eventAllowlist` values must include `pull_request.converted_to_draft` to enable this behavior. If the allowlist currently contains no `pull_request.*` entry, restart after adding it so TypeClaw re-registers the hook's coarse `pull_request` event.

### Push re-review

A push to an open PR (`pull_request.synchronize`) is not treated as a message. It re-checks the bot's own outstanding obligations on that PR — unresolved review threads it authored, and a standing `CHANGES_REQUESTED` — and wakes a session only when one is outstanding. Each unresolved thread is followed up in its own thread-scoped session, so a push and a human reply on the same thread cannot produce duplicate acknowledgements.

When a standing block also has to clear, one thread is designated the round's carrier and is alone eligible to submit the formal verdict, so concurrent siblings cannot land conflicting verdicts. Resolving a thread is never gated on carriership; it is gated only by GitHub's authoritative review state. If the carrier's turn ends without a verified verdict, another sibling is promoted. A round is bounded by a TTL and is dropped once expired or once the PR head moves on; `typeclaw doctor` reports a round still pending.

Requires `pull_request.synchronize` in `eventAllowlist`. It is in the shipped defaults, but a pinned `eventAllowlist` that omits it silently disables push re-review — `doctor` warns when that happens.

### Review check

With `review.check` on (the default), each review shows up as a check on the commit being reviewed, named after the agent's GitHub login (an App's `my-agent[bot]` shows as `my-agent`; `typeclaw/review` only if the login is not yet known). Several agents reviewing the same PR therefore get one check each. It is in progress while the reviewer works and completes when the review is verified on GitHub:

| Outcome                                                                     | GitHub App (check run) | PAT (commit status)        |
| --------------------------------------------------------------------------- | ---------------------- | -------------------------- |
| Reviewing                                                                   | `in_progress`          | `pending`                  |
| `APPROVE`                                                                   | `success`              | `success`                  |
| `COMMENT`                                                                   | `neutral`              | `success`                  |
| `REQUEST_CHANGES`                                                           | `failure`              | `failure`                  |
| Agent failure (reviewer error or timeout, review never posted, restart)     | `failure`              | `failure`                  |
| Cancelled (review request removed, PR converted to draft, review cancelled) | `neutral`              | `success` ("Not reviewed") |

A red check therefore means either requested changes or a review that did not happen; the check's description says which. Requesting the review again replaces it. A repository can make the check required in branch protection to gate merges on the bot's review; require it by the agent's name.

With a GitHub App, the check page also shows what the review is doing. While the reviewer works, it lists plain-language steps (reading the pull request, reading the code, running commands, writing up findings) with elapsed time and last activity, refreshed about once a minute. Once the review posts, the page summarizes the verdict, review duration, and a table of findings linking to their lines, and its **Details** link opens the review. Failures and skips state the reason and how to retry. The page never shows task or session ids, file paths the reviewer opened, commands, or model text. A PAT's commit status keeps its one-line description, now linked to the posted review.

The runtime owns the check's lifecycle, not the model. A durable lease is registered when the reviewer starts and is closed by whichever comes first: the verified review, the reviewer failing or being cancelled, a deadline sweep (the reviewer settling late, or a finished review never being posted), or the next adapter start after a restart. A check is never left in progress.

The check needs write access: the GitHub App needs **Checks: Read and write**; a PAT needs commit status write access (classic `repo:status`, or fine-grained **Commit statuses: Read and write**). Without it the check is skipped and the review still posts. The adapter logs one warning naming the missing permission (App installs are also checked at start).

### Missed review catch-up

Each adapter start, including tunnel-driven restarts, scans open PRs in `repos[]` in the background and replays those that still need the bot's review through the normal router path. It does not block adapter start. A PR is replayed at most once per cooldown: the adapter reserves a durable cooldown marker before routing and keeps it only when the router returns `accepted` or `duplicate`. An `observed`, `denied` or `control` receipt, or a routing failure, releases that attempt's marker so a later pass retries the PR; the failure is logged and the remaining PRs in the repository still run. A release removes only the marker this attempt created, never a newer attempt's. Stopping the adapter before a route is dispatched releases the reservation; stopping it afterward leaves the decision to that route's receipt and does not delay a replacement adapter. If the release itself cannot be persisted, the log says so and the PR stays in cooldown.

For `review.on: "opened"`, the scan only replays PRs created since the adapter was last alive (`channels/github-last-alive.json`). First boot uses boot time, so configuring a repository does not review its historical backlog. The marker is updated at boot, each reconcile tick, and stop.

Admitted review triggers are also saved in `channels/github-pending-reviews.json` before the router can start the work. This log covers opened, ready-for-review, bot review requests, blocking push re-reviews, and admitted scan replays. On every start, logged PRs are checked individually and replayed regardless of age or the scan cooldown, using a fresh boot identity so an interrupted admission cannot dedupe away its retry. Work the running process already admitted is skipped, so an adapter restart within the same process (a tunnel URL change, for example) does not run the same review twice. The scan skips logged work to avoid racing an in-flight review. A posted review at the logged commit or a descendant clears the entry, as do closing/merging the PR and converting it to draft. Boot checks also clear reviews that posted remotely just before a crash.

The log retains the admitted requester's identity; boot replay rechecks current permissions against that requester, not the PR author. An authoritatively verified dismissal also completes its matching pending re-review without clearing a newer head or admission. Boot uses the matching dismissal timeline event, rather than the review's original submission time, to recognize a dismissal that completed before a crash.

The start-time scan still catches a held `CHANGES_REQUESTED` whose commit predates the current head; periodic scans skip held reviews. Interrupted logged review turns get no restart notice because the log retains their retry obligation. Human comments and thread replies are not logged or automatically replayed; their existing recovery behavior is unchanged. `review.on: "off"` pauses review replay without discarding pending work.

## Webhook lifecycle

- Hooks auto-register for each entry in `repos[]` on start.
- On stop, only hooks created by this session are deleted.
- A ~2s delay before registration allows for Cloudflare edge warmup.
- On tunnel URL change, the adapter restarts and re-registers automatically.

## Config

### Letting channel members open PRs

Roles without `security.bypass.gitExfil` (such as member) can still push a branch to any repository listed in `repos`, so a member can ask the agent for a PR. Other `git push` destinations still need the bypass.

This is deliberately narrow. It needs GitHub App auth and applies only to a standalone `git push <remote> <branch>` (optionally `-u`) whose configured remote resolves to exactly one listed repository, with one plainly named branch. `src:dst` retargeting, `:branch` deletion, `+`/`--force`, tags, explicit URLs, and commands that also force-add, bulk-stage, re-point a remote, or upload files stay blocked. The push is funded with that repository's App token, and the agent then opens the PR with an explicit `gh pr create --repo … --head … --base … --title … --body …`.

Listing a repository in `repos` therefore authorizes publishing branch **content** to it for every role that can reach the agent; git objects are not scanned for secrets. Pair it with branch protection on the default branch, and scope `roles.member.match` to the people who should be able to ask for PRs — a signed webhook authenticates delivery, not the commenter's entitlement.

```json
{
  "channels": {
    "github": {
      "enabled": true,
      "webhookUrl": "https://hooks.example.com/github",
      "webhookPort": 8975,
      "repos": ["acme-corp/api", "acme-corp/frontend"],
      "review": { "on": "review_requested", "approve": true, "check": true },
      "engagement": {
        "trigger": ["mention", "reply", "dm"],
        "stickiness": { "perReply": { "window": 900000 } }
      },
      "history": {
        "prefetch": {
          "thread": { "head": 3, "tail": 10 },
          "channel": { "tail": 10 }
        }
      },
      "quotedReply": { "enabled": true, "queueDelayMs": 10000 }
    }
  }
}
```

Credentials live in [`secrets.json#channels.github`](/docs/reference/secrets-json).
